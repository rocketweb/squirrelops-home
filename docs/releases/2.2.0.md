## What is new in SquirrelOps Home 2.2.0

Home 2.2.0 turns more of what the sensor observes into alerts an operator can
act on, gives each install its own decoy presentation, and makes the Studio
Build Mac and mimic lifecycles recover from failures instead of saving them as
stops. It includes app 2.2.0 and sensor 2.2.0.

The app and native sensor require macOS 14 (Sonoma) or later on Apple Silicon.
Intel Macs are not supported.

### Studio logins are evidence

- An SSH or SMB login to the Studio Build Mac with the planted `buildbot`
  password is now a credential trip. It raises the same Critical alert as a
  submitted HTTP credential, naming the account, the protocol, and the source
  device. Failed logins are recorded as credential activity rather than
  scanning.
- Attribution is exact. The host assigns each relayed connection a source port
  inside the guest and reads the guest's own daemon logs over a fixed channel,
  so a login maps to one LAN peer with no inference from timing. The relays
  still carry opaque bytes and parse neither protocol. A guest without the log
  channel never publishes ports.
- A burst of simultaneous connections no longer resets some of them inside
  the guest. The guest listeners queue the full 16-connection ceiling, so the
  seventeenth connection is rejected by the host's capacity rule rather than
  by a dropped connection.

Shell commands and file operations inside the guest remain unobserved.

### Alerts that say what happened

- Device events are alerts. A new device or a device that needs verification
  raises a Medium alert while its trust is unknown or rejected, once per
  device, and approving the device silences both. A MAC address change on a
  known device raises a High alert regardless of trust, folded per device with
  the change history.
- Decoy alerts are titled and graded by what the visitor did. Write activity
  or ransomware intent on the Studio Build Mac is Critical. AI-agent probing
  and credential hunting carry those names at High. Severity only rises on a
  folded alert, and an escalation is delivered again to Slack and push as a new
  message.
- Trusted scanners. A device can be marked as a trusted scanner from its
  detail view. Its decoy connections are kept as evidence and counted, but they
  neither create nor feed Decoy Trip alerts. Credential trips stay Critical for
  every device. The decoy's responses to a trusted device are identical to its
  responses to anyone else.
- Sensor offline, delivered by the app. When the sensor stops answering for
  five minutes the app raises a Sensor Disconnected alert (High if the sensor
  had been reachable in this app session, Medium otherwise), posts it to
  Notification Center, and sends it to your Slack channel itself, because the
  sensor is the component that is gone. The app keeps the Slack webhook URL in
  its own Keychain entry, written only when you enter it in Settings.

### A response contract for your automations

The sensor detects and reports; it never blocks a device or changes a router.
For operators whose UniFi, OPNsense, or Home Assistant can act on an alert,
two new alert methods deliver one documented event, `squirrelops.alert/1`,
with the alert, the source device's IP and MAC, the decoy, and the campaign
intent and stage:

- **Automation Webhook** posts the event as JSON, signed with HMAC-SHA256 over
  a timestamp and the body when a signing secret is configured.
- **Home Assistant Events** fires `squirrelops_alert` through the existing
  LAN-only Home Assistant integration.

Both are off by default. The schema, signature recipe, and an example Home
Assistant automation are in `docs/ALERT_WEBHOOK.md`.

### Each install presents its own decoys

The classic decoys' source is public, and until now it also contained the
values they present. Server version strings, directory listings, login page
details, and application versions are now drawn per install from the
encrypted deployment secret, inside realistic distributions of what home
devices commonly run. The Studio Build Mac's project, repository, deployment
lane, model names, agent tool names, and ticket identifiers are drawn the same
way, consistently across its files and its model and MCP endpoints. Two
installs share nothing, a restart presents the same install, and the
repository no longer contains any install's presentation.

The guest image still fixes the hostname, user name, organization, and share
names; varying those is a later step.

### Studio Build Mac and mimic lifecycle

- A stopped Studio host stays listed on the Decoys tab with its host toggle
  off. The toggle is the only enable control, and the host was previously
  hidden from the view when stopped.
- Only an operator stop is saved as stopped. A Restart whose re-enable half
  fails, and an evacuation when a real device claims the Studio address, are
  saved as Degraded with the failure recorded. The Degraded badge carries the
  reason, including the claimant's MAC for an evacuation, and the host is
  retried on later scans and comes back on its own once the address is
  verified free. The sensor startup log states whether Studio is stopped on
  purpose or failed, with the reason.
- A mimic restart that dies after its listener came up now tells the app at
  once and records the failure on the saved rows, so the dashboard no longer
  shows services as active with nothing behind them. The fleet heals by
  replacement on the next scout cycle.
- Every enable, disable, and restart is written to the sensor log with the
  paired client that requested it and the outcome.

### Helper and packet filter reliability

- Port-forward loads get three minutes instead of thirty seconds, and helper
  requests wait their turn before their timeout starts, so a load issued
  during a network scan no longer times out in the queue.
- A load the helper did not answer in time is treated as unknown, not as
  rejected. Every load is named, the helper remembers the last one it applied,
  and the sensor asks which landed. A load that landed late keeps its mimic.
  A load that never applied is rolled back at once. An unanswered question
  schedules a retried reconcile, and the one-shot critical packet-filter
  failure is replaced by escalation only after six attempts fail.
- The helper verifies every mimic listener in one pass and names the exact
  endpoint and condition when one fails.

### Installation and configuration

- Upgrading on a Mac where the sensor service had been disabled with
  `launchctl disable` no longer fails to bootstrap the new sensor. The
  installer clears the override first and records launchctl's own error text
  in the install log.
- Every non-public alert-method field is treated as a credential: stored in
  the vault, redacted on read, and never written to the configuration file in
  plaintext. Previously only a named list of fields was vaulted.

### Release integrity and dependencies

- Dependency updates are grouped per ecosystem and reviewed together. This
  release updates FastAPI, Starlette, websockets, pydantic, aiohttp,
  cryptography, scapy, zeroconf, click, idna, ruff, and pyright in the sensor;
  the uv and Python base images of the sensor container; and the pinned GitHub
  Actions. The sensor image stays on its pinned Python minor.
- Sensor CI runs with the release's uv version. The release signing identity
  preflight is documented, including the email mismatch it catches.
- The guest image changes in this release (the relay shim, the log channel,
  and the listener backlog), so the release workflow rebuilds both
  architecture guests from the same pinned Alpine image digest and the
  complete package inventory as before.

The Studio persona runs on an isolated Linux guest with macOS-shaped files and
commands. It is not full macOS virtualization, and detailed operating-system
fingerprinting can identify the underlying guest.
